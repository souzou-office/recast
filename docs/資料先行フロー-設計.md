# 資料先行フロー（インボックス型）— 設計書

作成: 2026-07-09 / 状態: 検証済みドラフト v2（3視点レビュー反映済み）→ モックで流れを確認 → 実装

## 1. 目的と尺度

recast の核は「型にはめる」= 雑多なデータから、テンプレートに沿った出力を作ること。
その UX を、最小限の手間で済む形にする。

**効率の尺度（この設計全体の判断基準）**

人の手間は4種類に分解できる:

| 種類 | 内容 | 例 |
|---|---|---|
| 翻訳 | 現実をシステムの語彙に直す | 「役員増やしたい」→ メニューから「取締役就任」を探して押す |
| 転記 | どこかに書いてあるデータを入力欄に写す | 登記情報の商号をフォームに打つ |
| 判断 | 専門家にしか決められないこと | 書面決議でやるか実開催か |
| 確認 | 出てきたものが正しいか見る | プレビュー・チェック結果を見る |

**翻訳と転記は理論上ゼロにできる。判断と確認だけを人に残す。**

**対の制約（レビューで追加）**: 転記を確認に置き換えると、誤りの経路が「打ち間違い」から
「AI 誤読の見逃し」に移る。登記業務では後者の方が高くつく（補正・却下・職責）。
よって **「人が誤りに気づける確率を下げない」を対の制約とする** — 確認は必ず根拠
（出典・原文）とセットで見せ、1クリック確定の形骸化を設計で防ぐ（§7 誤りへの防御）。

## 2. 何を変えるか（一言で）

**入口の向きを反転する。**

- 今: 人が事由をメニューから選ぶ → 資料を出す → 質問に答える
- 新: **資料を放り込む → 事由の方から名乗り出る → 判断だけ聞かれる**

木構造（事由 = 判断・事実 → 書類・穴の対応表）はそのまま。穴埋めは決定論のまま。
変わるのは入口だけ。木があるから、AI の仕事は「登録済みのどの事由に当たるか」という
**選択肢が有限の分類問題**に縮む（extract-answers で questionId を enum で縛ったのと同じ設計パターン）。

**AI 境界の位置づけ**: 事由推定は新しい4つ目の境界ではなく、**境界①「資料から読む」の拡張**
（読む対象が「値」から「事由」に広がった）。有限選択肢・根拠必須・人が確定、の3点で
既存境界と同じ規律に従う。（memory の grand-design もこの表現に更新すること）

## 3. 前提条件（レビューで昇格した2点）

### 3-1. インボックスは「消えない器」であること

実務では資料は一度に揃わない（電話で受任 → 登記情報の取り寄せに数日 → 客から書類が後日届く）。
**資料の逐次追加**がこのフローの通常運転であり、追加のたびに事由推定・充当・プレフィルが
再評価される（増分更新）。よって「インボックス = 途中で消えない案件の器」はこの設計の
前提条件である。永続化の実装詳細（保存先・形式）は別管理でよいが、
「リロードや中断で資料と回答が消える」現状のままではこのフローは成立しない。

### 3-2. 事由推定の成立条件 — 依頼の意図が書かれたテキスト

登記情報・定款・株主名簿だけでは**現状**しか分からず、「これから何をするか」は原理的に
推定できない。推定の主根拠は**依頼の意図が書かれたテキスト**（お客さんのメール本文・電話メモ）。

- 段0の貼り付け欄は「電話・口頭の依頼はここに一言」と積極的に位置づける（一言あれば当たる）
- 原本しか無い束では「該当なし → 事由を手動選択」が**正規ルート**（敗北ではない）

## 4. 全体の流れ

```
段0 放り込む      人: 案件に関する資料をドロップ（逐次追加可）+ 依頼メモを貼り付け
                      ┊ 翻訳ゼロ・転記ゼロ
段1 事由が名乗る   AI: 資料 → 登録済み事由への分類（候補+根拠+前提）
                      + 各資料の種別分類（登記情報/定款/株主名簿/案件連絡/その他）
                  人: 提案カードを見て確定（前提と資料充当も同じカードで確認）……【確認】
段2 自動充当      機械: 木の requiredSources に AI 種別分類で充当、不足だけ提示
                  AI: fact 抽出（既存・キャッシュ付き）+ 回答プレフィル（既存）
                  人: 不足資料があれば追加ドロップのみ
段3 判断と残差    木: 判断（choice）・プレフィル済み回答・本当に足りない質問・注意書き
                  人: 判断を選ぶ + どこにも書いていない値だけ入力 ………………【判断】
段4 生成と検品    人: 生成ボタン（明示。自動では生成しない）
                  機械: 決定論生成（既存 produce） → AI: verify（既存+事由の当否観点）
                  人: プレビューとチェック結果を見る ……………………………………【確認】

  ※ 段1へはいつでも戻れる（事由の追加・差し替え）。同一 questionId の回答は保持される。
```

## 5. 各段の設計

### 段0: インボックス（入口）

- 画面: 大きなドロップゾーン + **テキスト貼り付け欄**（メール本文・電話メモ用。
  貼り付けは「メモ_日時.txt」として他ファイルと同列の資料になる — 既存 parseBuffer で流れる）
- 受けるもの: docx / xlsx / pdf（スキャン含む）/ txt / 画像。
  **スキャン PDF・画像はブロックしない**（既存の source-facts / extract-answers は
  document block / image block で既に読めている。ブロックは退行）
- 自動でテキスト化できない形式は「受け取ったが自動では読めない一覧」として**表示し続ける**
  （入れたのに無視された、を作らない）
- **eml は v1 非対応**（parseBuffer に無い・MIME 展開が要る）。貼り付け欄へ誘導。
  eml パーサ（本文+添付展開）は将来の拡張点として実装概略に記載
- 会社選択は不要（会社レスで開始）。fact 抽出済みの商号を正規化して既存会社と照合し
  （Company.name 部分一致 + profile.structured.商号）、一致すれば**紐付けを提案**（確定は人。
  一致ゼロなら会社レスのまま進む。紐付け確定後にはじめて共通フォルダの自動発見が有効になる）
- 資料の合計サイズを受付時にチェック（既存 MAX_TOTAL_BINARY_SIZE 相当）。
  サーバは資料を保持しない（Web 展開原則どおりクライアント保持）— ただし §3-1 の器の要件を満たすこと

### 段1: 事由の推定（AI 境界 = 境界①の拡張）

AI の仕事は**2つの分類を1回で**返す（どうせ全資料を読むので呼び出しは増えない）:

1. **事由の候補**（複数可）+ 根拠（どの資料のどの記述から）
2. **各資料の種別**（その事由の requiredSources の key / 案件連絡 / その他 — enum）

仕様の要点:

- tool use 強制・temperature 0・事由 id は enum。ただし**「該当なし」を必ず選べるスキーマにする**
  （候補ゼロ件を明示的に許す。enum 強制は「必ずどれかに寄せる」圧になるため、
  プロンプトに「近い事由に寄せるな。合わなければ該当なしと言え」を明記）
- プロンプト方針: **事由は「これから行う変更」**。依頼の意思表示（メール・メモ）が主根拠、
  原本（登記情報等）は現状の裏付け。原本にしか根拠が無い候補は確度を下げる
  （登記情報には過去の変更履歴が全部載っており、過去の事由を今回の依頼と誤読しやすい）
- 入力はコスト最適化: 各資料の先頭 N 文字のテキストで分類には足りる（全文不要）。
  資料一式の内容ハッシュでキャッシュ（source-facts と同じ方式 — 同じ資料なら同じ提案・AI ゼロ）
- 複数の会社・案件が読める場合（1通のメールに「A社の役員変更とB社の本店移転」）は
  **案件を分けて提案**する（人が採否）。v1 は「2件に分けて進めてください」の案内でよい

**提案カードの設計（確認の質を担保する要）**:

- 候補ごとに: 事由名 + 根拠（原文引用）+ **この事由の前提**（木の description と無条件 guards を表示。
  例:「取締役1名の会社で複数名選任する前提」）— 名前だけ合って前提が合わない木の
  ラバースタンプを防ぐ
- 近接候補が割れたとき（就任 vs 重任、代取変更 vs 就任）は**差が出るポイントを並記**
  （「現任の再任なら重任」）して能動的な選択にする
- 確定クリックは「事由 + 資料の充当結果」をまとめて確認する1クリック
  （現行の sourcesConfirmed を兼ねる）
- 外れた場合・該当なしの場合、3つの逃げ道:
  - a. 登録済みの事由一覧から手動選択（見落としだった場合）
  - b. **その場で覚えさせる** — 雛形フォルダ or 過去案件の完成品一式をドロップ + 「どうするか」を
    一言（例: 書面決議でやる。株主ごとに同意書1枚）→ 事由コンパイラが木+穴あきテンプレを生成
    （実値→【穴】変換 templateOps は実装済み）→ ツリービューでレビュー（赤=出所なしを潰す）→
    **そのままこの案件を通常フローで流す**。既存のコンパイル UI を「管理機能」から「該当なし直後の動線」へ移す
  - c. 雛形も過去例も無い完全な新種 → recast に無理に通さず1回目は人が Word で作る。
    その完成品が次回の b の入力になる（書類がマスターデータになる、の実例）

**旧チャット方式（AI が書類を直接書くレーン）はこれで畳む**（2026-07-10 決定）:
「初見は AI が捌く」の役目は b（その場で木を教える）が置き換える。AI が案件の書類本文を
直接書く場面はゼロになり、AI の失敗はコンパイル時（ツリーレビューと初回 E2E で捕捉）に限定される。
チャットタブ自体は会社との対話・横断検索用として残る。

### 段2: 自動充当

- **充当は AI の種別分類（段1の出力）を主とする。** ファイル名 patterns 照合は
  補助（AI を呼ばない再実行時・共通フォルダ自動発見用）に格下げ。
  理由: 客由来のファイル名は「scan001.pdf」「添付資料.pdf」で、名前照合では
  「入れたのに不足と言われる」偽不足が頻発し、人がリネームする＝翻訳の復活になる
- 充当結果は「登記情報 ← scan001.pdf」の形で表示し、**手動で割当し直せる**逃げ道を置く
- 同種資料が複数ある場合（古い登記情報も入れた等）: 採用した版と採らなかった版を明示。
  取得日が読み取れないときは人に選ばせる（無言で古い版を採らない）
- 不足があれば「不足: 株主名簿」を提示 → 追加ドロップ（段0の器に足すだけ）
- fact 抽出（既存 source-facts）への入力は **requiredSources に充当された資料だけに絞る**
  （現行 route.ts はドロップ全件を渡すため、雑多な資料が混ざると (a) メール記載の値が
  原本由来の顔をする (b) キャッシュキーが揺れて「同じ原本なら AI ゼロ」が死ぬ。要修正 — §8）
- 回答プレフィル（既存 extract-answers）への入力は種別分類で**案件連絡系に絞って**渡す
  （MAX_FILES=8 の切り捨て対策を兼ねる）。抽出結果は**全 questionId 分を保持**し、
  質問が波状に出現するたびに未入力欄へ適用する（現行は表示中の質問にしか当たらない。要修正 — §8）

### 段3: 判断と残差質問（木の仕事）

画面は3区画。**人の頭を使う所と見るだけの所を視覚的に分ける**:

1. **判断**（choice）: 決議方法など。専門家の言葉で聞く（テンプレ名では聞かない）。
   **プレフィル値があっても提案表示に留める**（「資料には『書面決議で』とあります（出典）」）。
   **人の明示クリックで確定** — 判断が無言で埋まる UI は「前提を無言で焼き込まない」原則に反する
2. **資料から埋まった値**: 2種類を区別して表示 —
   fact 由来（読み取り専用・根拠の原文引用付き）と、プレフィル由来（編集可・出典ファイル名付き）
3. **本当に足りない値**: 資料のどこにも書いていなかった質問だけ入力欄（同意日・報酬額など）

- guards（注意書き）は琥珀色で従来どおり。質問の波状出現も従来どおり
- 自動で読めなかった資料（スキャン等で失敗したもの）が不足の値に関係する場合:
  「この資料は自動で読めませんでした。値は手入力してください」と接続する
- **複数事由を採択した場合（v1 の割り切り）**: 事由ごとにセクションを分けて直列に処理
  （充当・質問とも独立。総会日を2回聞くのは許容）。束の合成は §10 スコープ外
- 事由の追加・変更はいつでも段1に戻れる。**同一 questionId の回答は保持**

### 段4: 生成と検品

- **生成は明示ボタンでのみ実行**（プレフィル確認は生成ボタンの手前。自動生成はしない — 既存原則）
- 決定論生成（produce）→ 書類リスト + 本体プレビュー
- AI チェック（verify）: 既存の観点（原本不一致・書類間不整合・日付順序・置換漏れ）に
  **「生成一式が依頼テキストの内容と合っているか（事由レベルの当否）」を1観点追加**
  — 誤分類は下流の書類が綺麗に出てしまい原本突合せでは捕まらないため、ここが最後の網

## 6. 手間の対照（現行 vs 新）

054 取締役就任クラス（メール1通 + 原本3点）での人の操作:

| 操作 | 現行 | 新 | 種類の変化 |
|---|---|---|---|
| 会社を選ぶ | メニューから1回 | 紐付け提案の確定1クリック | 翻訳 → 確認 |
| 事由を探して押す | メニューから1回 | 提案の確定1クリック（前提・充当込み） | 翻訳 → 確認 |
| 原本を出す | 受付画面でドロップ | 最初にまとめてドロップ（同じ） | — |
| 案件資料を出す | 質問画面でドロップ | 同上（同じ） | — |
| 質問に答える | 7問（プレフィル併用） | 判断1〜2 + 残差のみ | 転記 → 確認 |
| 生成・チェック | 確認 | 確認 + 事由の当否も網にかかる | — |

## 7. 誤りへの防御（確認の形骸化を防ぐ仕掛け）

1. 該当なしを構造的に言える分類スキーマ + 「寄せるな」プロンプト
2. 提案カードに前提（description + guards）を表示してから確定
3. 近接候補の差分ポイント並記（能動的選択化）
4. 判断のプレフィルは提案止まり、確定は人のクリック
5. 生成は明示ボタンのみ
6. verify に事由レベルの当否観点
7. 採用しなかった資料版の明示（古い登記情報を無言で採らない)
8. 読めなかった資料の一覧を表示し続ける

## 8. 木・エンジンへの影響（正直な版）

- **木の型: 変更なし。** select.ts / produce.ts / facts.ts: 変更なし
- **変更あり（小・要注意として明記）**:
  - route.ts: fact 抽出への入力を「充当済み資料のみ」に絞る(1行だが挙動が変わる)
  - 充当ロジック: 名前照合 → AI 種別分類を主に（名前照合はフォールバックへ）
  - extract-answers 周り: プレフィル結果の全量保持と波状適用(クライアント側)
- 新規: 事由+資料種別の推定 API(境界①の拡張)、インボックス UI
- 既存の「事由ボタンから始める」入口は**残す**（フォールバック。事由ボタンで始めた案件も
  途中からインボックスの配管に合流する — 資料の器は共通）

### 既存 UI との対応（作り直しではなく、入口の増築＋質問画面の区画整理）

| 既存 UI | 新フローでの扱い |
|---|---|
| 事由ボタン一覧 | 残す — 手動選択のフォールバックとして下へ |
| 受付（必要書類チェックリスト+ドロップ） | 残す — 充当表示は段1の提案カードに吸収。不足時は段2として単独表示 |
| 質問フォーム（choice/text/date） | 残す — 段3で「判断/読み取り済み/入力」の3区画に並べ替え |
| 質問カードのドロップゾーン（プレフィル用） | 統合 — 受付用と2箇所あったドロップをインボックス1つに一本化 |
| 出典・根拠表示 / guards 琥珀表示 | 残す — そのまま |
| 生成書類リスト+本体プレビュー | 残す — 段4そのまま |
| AI チェック | 残す — 事由当否の観点を1行追加 |
| 木構造ツリービュー / コンパイル UI | 無関係にそのまま |
| サイドバー・タブ構成 | そのまま（申請タブは会社レス開始、紐付け提案チップのみ新規） |

純粋な新規はインボックス（段0）と提案カード（段1）の2画面のみ。
- 既存5事由の **description バックフィル**が必要（「どんな依頼・言い回しがこの事由に当たるか」。
  これが無いと分類精度が最初から出ない）。コンパイラのプロンプトにも同じ指示を追加
  （事由を覚える瞬間に、名乗り方も覚える）

## 9. スケールの認識

全事由の name/description を1プロンプトに並べる分類方式は、事由数十件程度までの設計。
全業務対応で数百になったら業務領域での2段分類（法務→商業登記→…）に切り替える。
今は決めないが、この方式の賞味期限として認識しておく。

## 10. スコープ外（別の設計判断として保留）

1. **複数事由の束（1つの総会に複数議案 → 議事録1通に合成）** — 段1で複数提案・採択までは本設計。
   生成は事由ごとに別々（v1 の割り切り）。合成に進むかは実務頻度を見て判断（未決）
2. **fact による判断の自動化**（取締役会設置か等で分岐・既定値提案）— 段3の判断を減らす改良。
   フローの成立には不要
3. 案件の保存の実装方式 — ただし §3-1 の「消えない器」は前提条件なので、
   最低限の永続はこのフローとセットで入れる

## 11. モックで確認すること（次ステップ）

画面4枚 + **シナリオ3本**。幸福パス1本では設計の穴が見えない:

- シナリオ A（幸福パス）: メール + 原本3点を一括ドロップ → 事由が名乗る → 確定 → 判断1 + 残差 → 生成
- シナリオ B（資料が後から届く）: メモだけで開始 → 事由確定 → 不足表示 → 数日後に登記情報を追加 → 続きから
- シナリオ C（該当なし / 近接候補）: 原本のみで該当なし → 手動選択へ / 就任 vs 重任で候補が割れる → 差分表示で選ぶ

画面:
1. **インボックス**: ドロップ + 貼り付け + 読めない資料の一覧。「全部入れる」が伝わるか
2. **事由の提案カード**: 根拠・前提・資料充当・差分ポイント。1クリック確定が形骸化しない密度か
3. **判断と残差**: 「判断 / 見るだけ / 入力」の3区画が一目で見分けられるか。
   ここが一番大事 — 人の頭を使う場所が最小に見えなければこの設計は失敗
4. **生成と検品**: 既存の本体プレビュー + チェック結果 + 事由当否

確認の観点: 各画面で人がやることが「判断」と「確認」だけか。翻訳・転記が紛れ込んだら設計に戻す。
確認には必ず根拠が添えてあるか（対の制約）。

## 12. 実装の概略（モック確認後）

1. `/api/jirei/suggest` — 事由+資料種別の推定 API（tool use / 該当なし可 / temperature 0 /
   資料一式ハッシュでキャッシュ / 入力は各資料の先頭 N 文字 / モデルは分類問題なので Haiku も検討）
